1 — How to wire the theme JSON to your storefront CSS variables

The storefront template uses short CSS custom property names (--dark, --accent, --btn-font, etc.). The theme JSON returned by the API uses descriptive semantic names (background_color, button_color, button_font_color, etc.). You need a single bridge function. Call it once on page load, and again every time the user switches themes.

Critical rule: target the outermost storefront wrapper element, not document.documentElement. If you set variables on :root they have lower CSS specificity than class-level variable definitions already on the .sf wrapper. Setting them directly on the element as inline styles guarantees they win.

The applyTheme function — copy this exactly

// target = your outermost storefront wrapper (not document.documentElement)
function applyTheme(theme, target) {
  // ── Backgrounds ──────────────────────────────
  target.style.setProperty('--dark',         theme.background_color);
  // page background, hero overlay gradient base
  target.style.setProperty('--mid',          theme.surface);
  // topbar/navbar bg, toggle bar bg, sidebar bg
  target.style.setProperty('--card',         theme.card);
  // product card backgrounds, input fields

  // ── Brand / Accent ───────────────────────────
  target.style.setProperty('--accent',       theme.button_color);
  // buttons, active nav pills, badges, price text
  target.style.setProperty('--accent-light', theme.primary_light);
  // hover states, focus rings, subtle highlights
  target.style.setProperty('--btn-font',     theme.button_font_color);
  // text colour ON top of --accent buttons

  // ── Text ─────────────────────────────────────
  target.style.setProperty('--text',         theme.text_primary);
  // headings, product names, all primary copy
  target.style.setProperty('--muted',        theme.text_secondary);
  // descriptions, category labels, meta info

  // ── Borders ──────────────────────────────────
  target.style.setProperty('--border',       theme.border_accent);
  // card edges, dividers, input outlines
}

Where to call it in your React / Vue / vanilla app

// React example
const sfRef = useRef(null);

useEffect(() => {
  if (sfRef.current && store.selected_theme) {
    applyTheme(store.selected_theme, sfRef.current);
  }
}, [store.selected_theme]);

// JSX
<div ref={sfRef} className="sf">
  ... storefront content ...
</div>

// ──────────────────────────────────────────────
// Vue example
watch(() => store.selected_theme, (theme) => {
  applyTheme(theme, sfRef.value);
}, { immediate: true });

// ──────────────────────────────────────────────
// Multi-page apps: call on every page mount,
// not just the home page. Theme must be re-applied
// whenever a new root element enters the DOM.

2 — The 3 theme categories and why they behave differently

All 5 themes share the same JSON shape, but they fall into three fundamentally different rendering modes. Your frontend code does NOT change — but the values inside the JSON are inverted or shifted between modes. This is why applying a Bold theme with Classic assumptions produces a page that looks blank or broken.

Mode A — Brand on Light (Classic · Light · Soft)

Dark brand colour sits on a light/white page background.
This is the "normal" mode most designs expect.

— CLASSIC —
background_color → #F2EFEF              warm off-white
surface          → #E8E5E2              slightly darker off-white
card             → #FFFFFF              pure white cards
button_color     → #2e526b              dark brand blue
button_font_color→ #FFFFFF
text_primary     → #111111
border_accent    → rgba(46,82,107,0.25)

— LIGHT —
background_color → #FFFFFF              pure white
surface          → hsl(205,10%,95%)    near-white with tiny blue tint
card             → hsl(205,6%,97%)     near-white (barely tinted)

— SOFT —
background_color → #FAFAFA              near-white
surface          → #F0EDEA              warm light grey
button_color     → #627684              muted brand (desaturated)

Mode B — Brand on Dark (Dark theme)

⚠️ text_primary FLIPS from #111111 → #F5F2EE (off-white)
⚠️ button_color BRIGHTENS from #2e526b → #347eb2

background_color → #151a1e    near-black
surface          → #212a30    dark grey (navbar/sidebar)
card             → #29353d    dark card bg
button_color     → #347eb2    ← LIGHTER than classic brand
                              (brand is brightened for dark bg contrast)
button_font_color→ #FFFFFF
text_primary     → #F5F2EE    ← FLIPPED to off-white
text_secondary   → rgba(245,242,238,0.58)
border_accent    → rgba(52,126,178,0.25)

// Any hardcoded #111 text is invisible on #151a1e.
// Any hardcoded #fff card bg glows on dark page.
// ONLY var(--text) and var(--dark) work correctly.

Mode C — Brand Fills Canvas (Bold theme)

⚠️ background_color IS the brand colour (#347eb2)
⚠️ button_color FLIPS to #FFFFFF (white buttons)
⚠️ button_font_color FLIPS to #152632 (dark on white)
⚠️ text_primary FLIPS to #FFFFFF

background_color → #347eb2    brand blue IS the page bg
surface          → #274d68    darker brand shade
card             → #2d5e80    mid brand shade
button_color     → #FFFFFF    ← WHITE — not brand colour!
button_font_color→ #152632    ← DARK text on white button
text_primary     → #FFFFFF    ← white on brand bg
text_secondary   → rgba(255,255,255,0.65)
border_accent    → rgba(255,255,255,0.35)

// Any element with a hardcoded white (#fff) background
// will be invisible — it blends into the white buttons.
// Any hardcoded #111 text disappears on brand blue.
// Must use var(--dark), var(--text), var(--accent).

4 — CSS specificity: why you must target the element, not :root

Your storefront template defines CSS variables at class level (e.g. .sf { --accent: #2e526b; }). CSS specificity rules mean that a class selector beats the :root pseudo-class for variable inheritance when the variable is also defined on the same element. Setting variables on document.documentElement (which is :root) will be ignored if the element already declares the same variable via a class.

The fix is to set variables as inline styles on the wrapper element itself. Inline styles always beat class-level definitions, regardless of cascade order.

Wrong — variables silently ignored

// ❌ Sets on :root but .sf class overrides it
function applyTheme(theme) {
  document.documentElement
    .style.setProperty('--accent', theme.button_color);
  // .sf { --accent: #2e526b } in your CSS wins.
  // User switches theme → nothing changes visually.
}

Correct — inline style beats class

// ✅ Targets the wrapper element directly
const wrapper = document.getElementById('storefront-root');

function applyTheme(theme, el) {
  el.style.setProperty('--accent', theme.button_color);
  // This becomes: <div style="--accent:#347eb2">
  // Inline style specificity = highest possible.
  // Overrides .sf { --accent: #2e526b } every time.
}

applyTheme(selectedTheme, wrapper);
